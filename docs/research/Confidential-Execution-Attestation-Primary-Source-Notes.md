## What the sources actually establish

| Technology | Source-supported evidence | Important limit |
|---|---|---|
| AMD SEV-SNP | AMD's firmware ABI defines a guest report with `REPORT_DATA` (guest-supplied, 64 bytes), launch `MEASUREMENT`, guest policy, identifiers and TCB fields including `CURRENT_TCB` and `REPORTED_TCB`; signing can use VCEK or VLEK. The guest can place verifier-supplied challenge material in `REPORT_DATA`, but firmware does not interpret it. [AMD SNP firmware ABI, rev. 1.58, Tables 22–23](https://www.amd.com/content/dam/amd/en/documents/developer/56860.pdf). | A launch measurement is not a measurement of arbitrary subsequent application behavior. `REPORTED_TCB` can differ from current TCB, so comparing one field or only checking a signature is insufficient. AMD also defines host-requested reports, for which `REPORT_DATA` is zero-filled; a verifier must distinguish report source. [AMD SNP firmware ABI](https://www.amd.com/content/dam/amd/en/documents/developer/56860.pdf). |
| Intel TDX | The Linux kernel documentation describes a local `TDREPORT` containing guest build/boot measurements, platform security version, MAC and 64-byte caller-supplied `REPORTDATA`, commonly used for a verifier nonce. Remote verification requires conversion into a Quote through the quoting enclave. [Linux TDX guest documentation](https://docs.kernel.org/arch/x86/tdx.html). | A local MAC-protected `TDREPORT` is not itself a remotely verifiable Quote. A verifier still needs a valid quote chain, reference measurements, TCB appraisal and binding to its own challenge. [Linux TDX guest documentation](https://docs.kernel.org/arch/x86/tdx.html). |
| TPM measured boot | TPM PCRs and event logs provide measured-boot evidence; Linux can also collect runtime measurements through IMA. [TCG TPM 2.0 architecture](https://trustedcomputinggroup.org/resource/tpm-library-specification/), [Linux IMA documentation](https://docs.kernel.org/security/IMA-templates.html). | TPM measurements can help assess host state but do not encrypt a normal container's memory from the host administrator. Runtime coverage depends on what was actually measured and appraised; boot-only evidence must not be marketed as continuous runtime integrity. [IETF RATS architecture](https://www.rfc-editor.org/rfc/rfc9334.html), [Linux IMA documentation](https://docs.kernel.org/security/IMA-templates.html). |
| Confidential Containers / Trustee | Trustee separates an attestation service (evidence verification), reference-value provider and key broker. Its KBS API uses an attestation challenge, evidence and an attestation token; KBS applies resource policy before delivering secrets. Confidential Containers can measure Kata agent policy through init-data and supports runtime-attestation mechanisms. [Trustee project](https://github.com/confidential-containers/trustee), [KBS protocol](https://github.com/confidential-containers/trustee/blob/main/kbs/docs/kbs.yaml), [CoCo policies](https://confidentialcontainers.org/docs/attestation/policies/), [runtime attestation](https://confidentialcontainers.org/docs/features/runtime-attestation/). | Running Kata/CoCo components without supported confidential hardware does **not** create hardware-protected memory. Verification policy and secret-distribution policy are distinct. KBS token-verification documentation explicitly warns against accepting an untrusted embedded JWK in production. [CoCo development without confidential hardware](https://confidentialcontainers.org/blog/2024/12/03/confidential-containers-without-confidential-hardware/), [Trustee token verification](https://github.com/confidential-containers/trustee/blob/main/kbs/docs/attestation_token_verification.md). |
| Confidential GPU | NVIDIA's reference architecture lists supported combinations including H100, H200 and B200 with specified CPU TEE, GPU mode, drivers, runtime and Trustee versions; its GPU attestation requires a CC-capable SKU and compatible confidential VM. [NVIDIA supported-platform matrix](https://docs.nvidia.com/datacenter/cloud-native/confidential-containers/latest/supported-platforms.html), [NVIDIA GPU attestation guide](https://docs.nvidia.com/attestation/attestation-client-tools-sdk/latest/gpu_and_switch_attestation.html). | A generic “GPU present” or CPU TEE claim is not proof of confidential GPU execution. Hardware **and** firmware/driver/runtime/mode combinations must match a tested matrix, with CPU and GPU evidence appraised together. NVIDIA's support matrix is versioned and should be rechecked for procurement/deployment. [NVIDIA attestation architecture](https://docs.nvidia.com/datacenter/cloud-native/confidential-containers/latest/attestation.html). |

The IETF RATS architecture separates the **attester**, **verifier** and **relying party**: evidence is appraised against endorsement and reference values, and the relying party applies its own authorization policy to the result. It also distinguishes nonce/timestamp/epoch approaches to freshness. An authentic attestation result is **not** automatic authorization. [RFC 9334](https://www.rfc-editor.org/rfc/rfc9334.html).

## PSDC design implications to consider (proposals, not vendor requirements)

1. **Initial Basic profile:** use institution-owned admission, signed inventory, host hardening, workload isolation, network policy and monitoring without claiming host-operator memory secrecy. A TPM quote, where available, may strengthen host-state evidence but must not silently upgrade a node to Confidential.
2. **Later optional Confidential profile:** appraise the *actual CPU TEE* and, where used, the GPU evidence; bind a fresh verifier challenge, workload identity and requested key grant into the evidence/protocol; compare launch/runtime measurements and effective TCB against institution-approved reference values; check endorsement chains and revocation state; then apply a separate institution policy before a scoped key release. Fail closed for Confidential if any required evidence or authority is unavailable. This sequence is an architectural inference from [RFC 9334](https://www.rfc-editor.org/rfc/rfc9334.html), [AMD's report fields](https://www.amd.com/content/dam/amd/en/documents/developer/56860.pdf), [Linux TDX documentation](https://docs.kernel.org/arch/x86/tdx.html) and [Trustee's component split](https://github.com/confidential-containers/trustee).
3. **Freshness policy remains to be chosen:** a verifier-generated single-use nonce is a sound protocol candidate; PSDC still needs to define challenge lifetime, replay cache, clock-skew treatment, attestation-result lifetime, renewal trigger, reference-value update process and revocation propagation. Do not claim that a report's timestamp alone proves freshness. [RFC 9334, freshness discussion](https://www.rfc-editor.org/rfc/rfc9334.html), [Trustee KBS challenge fields](https://github.com/confidential-containers/trustee/blob/main/kbs/docs/kbs.yaml).
4. **Separate assurance claims:** host admission/identity, execution confidentiality, integrity measurement, usage metering and result correctness need distinct evidence. A TEE report does not prove that an application returns a correct result; a signed receipt does not prove host-memory secrecy. This separation follows the different evidence and relying-party roles in [RFC 9334](https://www.rfc-editor.org/rfc/rfc9334.html).
5. **Institutional sovereignty:** run the verifier, reference-value policy and key-release authority under each institution's control where feasible. Any outside endorsement or vendor certificate dependency must be named, cached/renewed under an explicit policy and tested for outage; do not imply a fully offline confidential profile until it is actually demonstrated. Trustee can be self-hosted but still appraises hardware-specific endorsements. [Trustee project](https://github.com/confidential-containers/trustee), [RFC 9334](https://www.rfc-editor.org/rfc/rfc9334.html).
